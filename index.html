Profile

My research interests are computer architecture and hardware design productivity: hardware construction languages, out-of-order processor generators, FPGA accelerators for machine learning, and HW/SW co-design.

In my third undergraduate year, I studied computer architecture on my own, from online material. I then tried to write an out-of-order superscalar RISC-V CPU without supervision. The work was much harder than I expected, and I did not finish it. That attempt decided the direction of everything I have done since. As a master's student, I first built the tool I had been missing: Kathryn, a framework that hides many of the low-level design tasks. Chisel was the inspiration. I then used Kathryn to build Kride, an out-of-order RISC-V core that re-implements the RIDECORE microarchitecture and runs programs compiled with the standard GCC toolchain. Kathryn is published as a first-author paper in IEEE TCAD, 2026. My current work, Carolyne, builds on Kathryn to generate one out-of-order engine for many instruction sets.

At CERN, I studied partial reconfiguration for machine learning on FPGAs. With partial reconfiguration, an FPGA can load new parts of itself while it is running. A small FPGA cannot hold a whole model, but it can still run one, by loading one part of the model at a time. This work became DFX4ML. I also wrote the Vitis Unified backend for hls4ml, which is now merged into hls4ml.

Kathryn: cycle-accurate hardware design framework Chulalongkorn University

A hardware construction framework with abstract control flow, decentralized update, and hardware aggregation, with no structural RTL. Published in IEEE TCAD, 2026.

github.com/Tanawin1701d/Kathryn · pypi.org/project/kathryn · kathryn-tools.org

IEEE TCAD, Early Access, 2026 · doi

  • Hybrid Design Flow: control flow as blocks; stalls, kills, and back-pressure are handled by the framework.
  • Decentralized update: a resource is updated where the event happens, not at one driver.
  • Hardware Aggregator: many entries managed as one bundle.
  • Result: 67.85%, 63.55%, and 56.67% fewer control, data, and total lines than the RIDECORE Verilog, 100% cycle-accurate. The paper also gives a qualitative comparison with Chisel.
  • Known limit: simulation is about 16× slower than Verilator-compiled RIDECORE (140.7 s against 8.9 s). Future work: optimize the generated HDL and study large-scale designs.
  • Size: the C++ version in the paper is 27,321 lines of code, 98.5% hand-written. It is now rewritten as Python on a Rust engine (PyO3, about 14k lines, AI-assisted under fine-grained human control), on PyPI: pip install kathryn.

Kride: out-of-order superscalar RISC-V core Chulalongkorn University

An out-of-order superscalar RV32IM core written in Kathryn, re-implementing the RIDECORE microarchitecture, and the case study of the IEEE TCAD paper. It runs programs compiled with the standard GCC toolchain.

kathryn-tools.org/cppbook/kride · built in the Kathryn repository, src/example/o3

  • All core logic is hand-written: six stages, five reservation stations, a reorder buffer, and five speculative tags.
  • Bit-exact against RIDECORE over ten workloads and 2.2M cycles.
  • Runs GCC-compiled programs on a Kria KV260, cycle for cycle equal to simulation.

Carolyne 0.1: ISA-agnostic out-of-order CPU generator current research

One out-of-order engine, many ISAs. An ISA is a small Python description, and the engine generates the decoder, rename, register files, and commit. Built on Kathryn, since Aug 2026.

github.com/Tanawin1701d/Carolyne · kathryn-tools.org/carolyne

  • RV32IM and MIPS32r2 (user-level subsets, no system or CSR instructions) on one two-wide engine.
  • Each ISA description is only about 600 lines; the shared engine is about 4,300.
  • 17 C programs (-O0, -O2) match host execution on both ISAs in Verilator. MIPS32 passed all 34 runs with no change to the engine.
  • Highly object-oriented: ISAs, stations, and execution units extend shared base classes.
  • Long-term goal: a universal microarchitecture modeling framework for CPUs, DSPs, and accelerators, where humans and AI explore hardware designs together.

DFX4ML: CPU-free partial reconfiguration for ML inference CERN

Runs a model too large for the FPGA by reconfiguring parts of the FPGA during inference.

github.com/Tanawin1701d/dfx4ml_infra · presentation

Technical report v1.0 beta · PDF

  • Verilog state machines drive ICAP, so the FPGA fabric reconfigures itself with no CPU in the loop.
  • Reconfigures at 381 MB/s (2.9 MB in 7.4 ms), about 95% of the ICAP limit at 100 MHz.
  • Two regions ping-pong, so one computes while the other is reloaded.
  • A Python flow splits a Keras model with hls4ml and builds every bitstream. Tested on a Kria KV260.
  • Ongoing: solving the on-chip buffer capacity and DDR4 bandwidth limits.
  • Built at CERN under the supervision of Nicolò Ghielmetti, and presented at the CERN Edge SpAIce technical meeting.

HDL and Vivado + MCP Support: IntelliJ IDEA plugin

Verilog and SystemVerilog tooling for IntelliJ IDEA that gives a live Vivado session to an AI assistant over the Model Context Protocol. 2,000 downloads on the JetBrains Marketplace.

JetBrains Marketplace · github.com/Merge-Panic-Society/JetBrain-Verilog-Vivado-Plugins

2,000 downloads · rated 4.4

  • MCP server: thirty parameter-checked Vivado commands, from project creation to bitstream and programming. Safety-gated: loopback host only, a per-session bearer token, and raw Tcl behind an opt-in.
  • Language support: highlighting, completion, and cross-module linting for Verilog, SystemVerilog, Tcl, and XDC, through Icarus Verilog or Verilator.
  • Simulation and waveforms: run a testbench and read the VCD in an in-IDE waveform viewer, which the assistant can drive as well.
  • Vivado console: a bidirectional Tcl terminal over a socket, so the Vivado GUI stays usable while commands run.
  • Written in Kotlin on the IntelliJ Platform, for IntelliJ IDEA 2025.1 and later.
